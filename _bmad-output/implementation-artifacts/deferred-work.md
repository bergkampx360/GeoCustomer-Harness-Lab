## Deferred from: code review of story-1.5 (2026-07-18)

- No stable tie-break for customers with duplicate `name` and equal raw distance — `prisma.customer.findMany()` has no `orderBy`, and `sortByDistance`'s comparator returns `0` for equal name + equal raw distance, so relative order would depend on Postgres's unordered scan. The Prisma `Customer` schema's unique constraint is `[name, telepules, countryCode]`, not `name` alone, so two same-named customers are legally possible. Deferred because the actual bundled seed dataset (`data/seed-customers.json`, 15 rows) has 15 unique names — currently unreachable — and AC5 only requires a name tie-break, not handling of duplicate names.
- `haversineKm`'s intermediate `h` term (`sin²(dLat/2) + cos(lat1)·cos(lat2)·sin²(dLon/2)`) is not clamped to `[0,1]` before `Math.asin(Math.sqrt(h))`; floating-point overshoot for near-antipodal or coincident-boundary coordinate pairs could yield `NaN` instead of a distance. Deferred because every coordinate in this project's domain (Budapest + bundled Central-European settlement references) is geographically close, never near-antipodal, so the branch is unreachable with real data.
- The `customers.spec.ts` "rounds distanceKm to one decimal" test (`expect(Number.isInteger(vienna.distanceKm * 10)).toBe(true)`) only proves the value has one decimal place, not that it equals the correct ≈214 km — it would pass for any wrong one-decimal value. Deferred as a test-quality gap, not a functional defect: the actual Vienna distance correctness is independently proven by `distance.spec.ts`'s direct `haversineKm(BUDAPEST, VIENNA)` tolerance assertion.
- No test exercises the partial-null coordinate case (`lat` set, `lon: null`, or vice versa) even though `sort.ts`'s ternary explicitly special-cases it. Deferred as a coverage gap only — the existing ternary (`customer.lat !== null && customer.lon !== null ? {...} : null`) already handles this branch correctly by falling through to the null path.
