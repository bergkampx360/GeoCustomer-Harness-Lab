- (capability) CAP-1 intent: client retrieves total seeded customer count via GET /customers/count. success: response is count field equal to actual row count. source: assignment.md GET /customers/count section
- (capability) CAP-2 intent: client retrieves all customers ordered ascending by distance from Budapest via GET /customers/by-distance, each annotated with distanceKm. success: distanceKm rounded to one decimal; Budapest customers first at 0 km; unresolved-coordinate customers last with distanceKm null; ties broken by name ascending. source: assignment.md GET /customers/by-distance section
- (capability) CAP-3 intent: system idempotently loads the fixed seed file and offline-geocodes each customer settlement to lat/lon via a bundled local reference, no external calls. success: running seed twice yields no duplicate rows; matched settlements get non-null lat/lon; unmatched settlements get null lat/lon, are logged, and do not stop processing. source: assignment.md BETOLTES section
- (constraint) Data model minimum: customers table has id, name, telepules (settlement), lat nullable, lon nullable. budget and note may optionally be stored but are not required. source: assignment.md ADATMODELL
- (constraint) Seed input file is data/seed-customers.json containing 15 customers with fields name, budget, location.city, location.countryCode, note. location.city is the settlement/telepules. source: assignment.md ADAT
- (constraint) Original seed data file data/seed-customers.json must not be modified. source: technical-constraints.md Seed data
- (constraint) Settlement matching for geocoding must be accent-independent, case-independent, and whitespace-trimmed. source: assignment.md BETOLTES bullet list
- (constraint) Budapest, and optionally its districts (kerulet), must resolve to the capital in the settlement reference. source: assignment.md BETOLTES
- (constraint) If a settlement is absent from the reference: lat/lon = null, this is not an error, must not crash, must be logged, processing continues for remaining rows. source: assignment.md BETOLTES
- (constraint) Seed process must run separately from the HTTP API through a dedicated command, and must never be exposed as an HTTP endpoint. source: technical-constraints.md API and Database sections, consolidated with assignment.md GET endpoints list which lists only count and by-distance
- (constraint) Only GET /customers/count and GET /customers/by-distance are exposed. No POST, PUT, PATCH or DELETE endpoints of any kind. source: technical-constraints.md API section, consolidated with assignment.md VEGPONTOK which lists only these two
- (constraint) distanceKm is rounded to one decimal place in the by-distance response. source: assignment.md GET /customers/by-distance rules
- (constraint) Runtime: Node.js LTS. Language: TypeScript with strict mode enabled. Package manager: pnpm. source: technical-constraints.md Runtime and language
- (constraint) Repository must be an Nx monorepo, kept small and appropriate for the project size; avoid unnecessary packages, layers, abstractions and infrastructure; no frontend application. source: technical-constraints.md Repository structure
- (constraint) API framework: Fastify. source: technical-constraints.md API
- (constraint) No authentication or authorization is implemented. source: technical-constraints.md API, consolidated with Scope control exclusion list
- (constraint) No runtime LLM calls and no external geocoding API calls at any point; service must run fully offline. source: assignment.md opening line about no external geocoder API and no LLM calls at runtime, consolidated with technical-constraints.md API section same two rules
- (constraint) Database: PostgreSQL, run locally via Docker Compose. source: technical-constraints.md Database
- (constraint) Prisma is used for schema definition, migrations, seed, and typed database access. source: technical-constraints.md Database
- (constraint) Testing framework: Vitest. Haversine distance calculation must have unit tests. source: technical-constraints.md Testing, consolidated with assignment.md TESZT section
- (constraint) PostgreSQL MCP must be configured and must actually be used during development, not just configured. source: technical-constraints.md PostgreSQL MCP, consolidated with assignment.md closing line about wiring the Postgres MCP

- (assumption) Only PostgreSQL itself is required to run via Docker Compose (technical-constraints.md says PostgreSQL must run locally through Docker Compose); neither source document states the Fastify API process itself must be containerized, so the app is assumed to run directly via pnpm/node against the Dockerized Postgres. Flagged as assumption, not silently baked into a constraint.
- (assumption) Node.js LTS is treated as whichever LTS release is current at implementation time, since neither document pins an exact version.
- (question) Neither source document states whether location.countryCode from the seed input (present alongside name, budget, location.city, note) should be persisted on the customers table. The documented minimum data model (id, name, telepules, lat, lon) plus the explicitly-optional budget and note fields does not mention countryCode at all. Needs a human decision before the Prisma schema is designed.
- (question) Neither source document names a specific PostgreSQL MCP server/tool to configure, nor defines precisely what project-scoped configuration means (e.g. a repo-local MCP config file vs. a user-global one). Both documents require MCP to be configured and actively used, but the concrete package/setup choice is unresolved. Needs a human decision before development tooling is set up.

- (decision) Approved: persist location.countryCode on the customers data model, alongside id, name, telepules, lat, lon, optional budget/note. Rationale: present in the authoritative seed input; supports deterministic offline location resolution; can participate in reliable idempotent seed identification. Data-model decision only, not a new API capability -- countryCode must not appear in any API response since neither frozen source document requires it.
- (decision) Approved definition of project-scoped PostgreSQL MCP configuration: configuration is stored in the repository; must work from a fresh clone after documented local setup; connection details and secrets come from environment variables; no password, token, or local secret may be committed; the MCP must be actively used during development or verification as the source documents require. Concrete MCP server package, Docker image, and launch mechanism are explicitly deferred to the architecture phase, not decided in the spec.

SPEC.md Open Questions section removed (empty per template convention). - (decision) Resolved readiness finding M-1: sorting for GET /customers/by-distance is by the raw, unrounded Haversine distance -- never by the rounded distanceKm value. distanceKm remains rounded to exactly one decimal place (per docs/assignment.md's 'egy tizedesre kerekives', unchanged) but that rounding is display-only and happens after sorting. The name tie-break applies only when two customers' raw distances are exactly equal, not when their rounded distanceKm values merely coincide. Null-handling and Budapest-first/unresolved-last placement are unchanged. This is a clarification of the frozen assignment (which separately describes rounding of the displayed field and ascending distance order, without stating which value is the sort key), not a new capability -- CAP-2 is unchanged, only its success criterion is made unambiguous. SPEC.md CAP-2 and api-contract.md's Distance and sorting rules section updated accordingly.
