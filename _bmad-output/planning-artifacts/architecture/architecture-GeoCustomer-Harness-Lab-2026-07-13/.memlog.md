- (version) PostgreSQL MCP server choice researched: official @modelcontextprotocol/server-postgres was archived July 2025 with an unpatched SQL injection vulnerability -- must not be used. Community-maintained crystaldba/postgres-mcp (PyPI package postgres-mcp, MIT license, ~2.4k stars) is the current recommended replacement, run via uvx postgres-mcp --access-mode=restricted, configured entirely through env vars (DATABASE_URI).
- (decision) AD-1 Design paradigm: Transaction Script (Fowler). Binds: CAP-1, CAP-2, CAP-3. Prevents: the two independent harness implementations building incompatible layering (one flat, one repository/service/DDD-layered), which would make them structurally incomparable and adds ceremony the constraints explicitly forbid. Rule: each route handler is one top-to-bottom function (transport -> domain function(s) -> response shape); no repository/service/interface abstraction layers; domain logic (Haversine, sorting, normalization) is plain exported functions, not classes.
- (decision) AD-2 Nx workspace layout: single Nx project, apps/api. Binds: all. Prevents: unnecessary Nx project-boundary ceremony (a lib with exactly one consumer) or, conversely, dropping Nx conventions altogether. Rejected alternative: a second Nx lib for pure domain logic -- rejected because there is only one consuming app, so a project boundary buys nothing a folder boundary doesn't already give, and technical-constraints.md explicitly says keep the monorepo small and avoid unnecessary layers. Rule: exactly one Nx project (apps/api); internal folders (src/routes, src/domain, src/geo, src/db, prisma) provide separation, not a second Nx project.
- (decision) AD-3 Fastify application boundary: Binds: CAP-1, CAP-2. Prevents: business logic leaking into route registration, or the Fastify instance being duplicated/rebuilt differently between the running server and its tests. Rule: src/app.ts exports buildApp() returning a fully-configured Fastify instance with routes registered and no .listen() call; src/server.ts is the only file that calls buildApp().listen(...) and wires process shutdown; tests import buildApp() directly instead of starting a real listening server.
- (decision) AD-4 Prisma placement and client lifecycle: Binds: CAP-1, CAP-2, CAP-3. Prevents: two independently-instantiated Prisma Clients (e.g. one per request, or separate ones in the server and the seed script) causing connection-pool exhaustion or schema drift. Rule: one schema at apps/api/prisma/schema.prisma, migrations in apps/api/prisma/migrations/ (Prisma's default), one generated client; one shared src/db/client.ts exporting a single lazily-created PrismaClient singleton, imported by both server.ts and seed.ts; nothing else instantiates PrismaClient directly.
- (decision) AD-5 Seed separated from HTTP server, with idempotency mechanism fixed: Binds: CAP-3. Prevents: seed logic reachable over HTTP, the server auto-seeding on boot, or two independently-built idempotency strategies (wipe-and-reinsert vs upsert) behaving differently under re-runs. Rule: seed logic lives only in src/seed.ts, run via its own command (e.g. nx run api:seed), never imported by app.ts/server.ts; idempotency is enforced via a Prisma @@unique([name, telepules, countryCode]) constraint on Customer (the closest available natural key, per the approved countryCode decision) and the seed uses upsert keyed on that triple, not a truncate-and-reinsert; the process disconnects Prisma and exits after running.
- (decision) AD-6 Offline settlement reference placement and normalization: Binds: CAP-3. Prevents: two independently-built normalization functions disagreeing on case/accent/whitespace handling and producing different geocoding outcomes for the same input. Rule: reference data lives in one file, src/geo/settlement-coordinates.ts (plain exported map, not a DB table); one exported normalizeSettlementName() (Unicode NFD-normalize + strip diacritics + lowercase + trim) is the only place normalization happens; Budapest district/kerulet aliases live beside the reference and resolve through the same function to the capital's coordinates.
- (decision) AD-7 Haversine and sorting boundary: Binds: CAP-2. Prevents: distance/sorting logic duplicated or reimplemented differently between the route handler and its tests, or coupled to Fastify/Prisma types so it cannot be unit tested without a database. Rule: src/domain/distance.ts exports pure haversineKm(a, b); src/domain/sort.ts exports pure sortByDistance(customers) implementing null-last-with-name-tiebreak; neither module imports Fastify or Prisma types; the route handler is the only caller wiring them to real data.
- (decision) AD-8 Vitest placement and categories: Binds: CAP-1, CAP-2, CAP-3 (testing). Prevents: the mandatory Haversine unit tests accidentally requiring a live Postgres to run, making CI slow or flaky. Rule: unit tests are co-located *.spec.ts next to the pure modules they test (src/domain/distance.spec.ts, src/domain/sort.spec.ts, src/geo/normalize.spec.ts) and must not import Prisma or start Fastify; any endpoint-level test touching a live DB is a separate, explicitly optional integration test, not part of the default required test target.
- (decision) AD-9 Docker Compose PostgreSQL setup: Binds: CAP-3, dev workflow. Prevents: divergent ad-hoc local Postgres setups (native installs, mismatched ports) that make fresh-clone reproducibility unreliable. Rule: one docker-compose.yml at repo root with one postgres service pinned to postgres:18-alpine, a named volume for persistence, and credentials/db-name/port sourced from .env (values placeholder-only in committed .env.example); DATABASE_URL for Prisma is assembled from those same env vars.
- (decision) AD-10 Project-scoped PostgreSQL MCP configuration: Binds: dev workflow, SPEC MCP requirements. Prevents: MCP setup requiring machine-specific manual steps that break on a fresh clone, or secrets committed. Rule: MCP server is postgres-mcp (crystaldba, PyPI), launched via uvx postgres-mcp --access-mode=restricted; its configuration (a repo-committed .mcp.json, Claude Code's project-scoped convention) references DATABASE_URL from the environment and never inlines a connection string; works after docker compose up plus copying .env.example to .env on a fresh clone; restricted/read-only access mode matches the SPEC's inspect-only MCP usage.
- (decision) AD-11 Clean shutdown and error-handling boundaries: Binds: CAP-1, CAP-2, server lifecycle. Prevents: the process hanging on SIGTERM (leaked DB connections) or an unhandled route error crashing the process or leaking a stack trace to the client. Rule: server.ts registers SIGINT/SIGTERM handlers that call app.close(), which via Fastify's onClose hook disconnects the shared Prisma client before the process exits; Fastify's global error handler catches thrown errors, logs them via Fastify's built-in logger, and returns a generic error JSON body -- no unhandled rejection is allowed to crash the process silently.
- (direction) Rejected overengineering options (recorded for traceability, not adopted): repository/service/DDD layering (Transaction Script chosen instead -- no second consumer, no complex business rules); a separate Nx lib for domain logic (single Nx project chosen -- only one consumer app); a message-queue/event-driven seed pipeline (excluded scope bans message queues/event sourcing; seed is one dedicated batch command); PostGIS or DB-side geospatial functions for distance (excluded scope bans PostGIS; Haversine in application code is mandated and sufficient for 15 rows); an external geocoding API or coordinate cache (offline mandate + excluded scope; a bundled static reference is required and sufficient); a custom API error-envelope/problem-details middleware (only two read-only endpoints, no client contract requires one; Fastify's default error handling suffices); a cache (Redis or in-memory) in front of by-distance (15-row table, no performance requirement in SPEC); a mandatory e2e/integration Nx test project against a live Postgres (kept optional per SPEC's 'additional tests only when clear value', not a default target); containerizing the Fastify API itself in Docker Compose (SPEC's own Assumption already scopes Docker Compose to Postgres only).
- (assumption) Id strategy for Customer.id: Int with @default(autoincrement()). Not elevated to an AD -- the id is never exposed as a stable external identifier and nothing else in this single-service system depends on its format, so two independently-built harnesses choosing differently could not actually diverge incompatibly within this spine's own scope.
